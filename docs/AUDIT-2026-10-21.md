# AS Physics Trainer — audit et première stabilisation

Date : 21 octobre 2026. Base examinée : `c85843700e15812fb71d94473d58f3c92a4d5844`.
Branche de travail : `dev/stability-audit-2026-10-21`. Aucune publication sur main.

## Verdict

Le prototype convient à une phase de test accompagnée. La diffusion comme banque de questions entièrement fiable demande encore une validation sur les QP/MS originaux. La version de développement corrige plusieurs risques techniques, mais n'est pas déclarée validée sur tablette ni sur l'ensemble des PDFs.

## Périmètre et architecture

Les six fichiers suivis du dépôt initial ont été examinés : `index.html`, `style.css`, `app.js`, `config.js`, `questions.json`, `README.md`. Aucun framework, serveur applicatif, compte ou collecte distante de résultats. GitHub Pages sert les fichiers ; PDF.js 4.10.38 et MathJax 3 viennent de jsDelivr. Une panne de chargement du module PDF.js peut empêcher le démarrage avant l'exécution du code applicatif.

Les PDFs proviennent des fichiers locaux sélectionnés. Ils ne sont pas dans le dépôt et le code examiné ne les téléverse pas. Le dossier mémorisé est stocké dans IndexedDB (`physics-trainer-folders`, store `handles`) ; son autorisation reste contrôlée par le navigateur. Les résultats sont dans localStorage, clé historique `mms_physics_web_v05` conservée. Historique limité à 500 ouvertures, sessions terminées à 100 ; autoévaluations Paper 2 et réponses QCM conservent la dernière valeur par question. Le code de classe dans config.js est public : écran de commodité, aucune authentification. Aucune migration Microsoft 365 entreprise.

## Problèmes priorisés

| Priorité | Constat sur la version initiale | Traitement / suite |
|---|---|---|
| P0 pédagogique | Aucune validation complète traçable des 414 entrées | Avertissement visible ; ne pas présenter les scores comme une validation officielle |
| P0 technique | `attempts[q.id]` bloque définitivement une nouvelle réponse après remise à zéro des questions vues | Corrigé : une tentative par question **dans la session**, nouvelles tentatives autorisées dans les suivantes |
| P0 technique | La session utilise les chapitres sélectionnés à chaque tirage, tandis que son résumé conserve ceux du départ | Corrigé : banque de tirage fondée sur les chapitres figés au démarrage |
| P0 technique | Question en attente déduite de l'écran courant ; navigation/historique/changement de mode peuvent perturber la session | Corrigé : `pendingId` sauvegardé, reprise explicite, consultation sans score hors question attendue |
| P1 technique | Historique d'une ancienne question peut afficher des boutons actifs sans session valide, puis un retour trompeur | Corrigé : consultation seule ; aucun enregistrement hors question attendue |
| P1 technique | Les boutons A–D sont utilisables pendant le rendu ou après échec du PDF | Corrigé : activation uniquement après rendu réussi |
| P1 sauvegarde | localStorage.setItem non protégé : quota ou stockage interdit interrompt l'action | Corrigé : message d'échec visible, session en mémoire, export JSON indépendant du succès de sauvegarde |
| P1 rendu | PDF Paper 2 non détruit après utilisation ; rendu ancien susceptible d'écrire sur le nouveau panneau après un await | Corrigé : instantané des pages/échelle, contrôles de rendu, destruction dans finally ; même nettoyage Paper 1 |
| P1 ergonomie | Favoris et cases « Needs revision » enregistrés mais pas de liste dédiée pour les retrouver | Listes dédiées ajoutées, incluant les dernières erreurs QCM |
| P1 apprentissage | Tous les QCM vus = arrêt jusqu'à Reset seen ; absence de révision des erreurs | Nouvelle session possible ; priorité aux questions inédites puis erreurs, puis succès, sous réserve de diversité des groupes récents ; aucun doublon exact dans une session |
| P1 pédagogie | 5 explications QCM et 9 solutions structurées seulement | Inchangé : enrichir après validation des sources ; aucune explication officielle inventée |
| P1 cadrage | 63 QCM ont un cadrage de plus de 650 points PDF | Liste dans index-audit.json ; bouton pleine page ajouté, sans modifier les cadrages sur hypothèse |
| P2 ergonomie | Absence de bilan individuel par chapitre | Tableau ajouté : réponses QCM des sessions conservées, dernière autoévaluation Paper 2 ; questions multi-chapitres comptées dans chacun |
| P2 dossier | Impossible de choisir un autre dossier mémorisé via le bouton existant ; persistance IndexedDB bloquante | Bouton de changement ajouté ; lecture possible même si mémorisation impossible ; doublons de noms dans une sélection exclus |

| P2 sauvegarde | Données liées à l'origine/navigateur/appareil, aucune sauvegarde externe | Export JSON ajouté ; import/restauration reste à implémenter et tester avant de promettre la portabilité |

## Banque de questions : ce qui est établi

414 identifiants uniques ; 263 QCM et 151 questions structurées. Aucun doublon exact `(qp_file, question)`. Cela ne permet pas d'exclure les redondances conceptuelles, des numéros erronés ou des questions équivalentes entre variantes.

Les 414 références de source sont syntaxiquement cohérentes avec les noms QP/MS, les pages/ranges sont correctement formés, les 263 réponses QCM appartiennent à A–D. Ce contrôle ne prouve pas que les fichiers existent, que les pages correspondent à la question, que les marks sont exacts ou que la bonne lettre est correcte.

Métadonnées de classement : 187 `automatic-provisional`, 4 `checked-by-question-wording`, 223 sans statut. « checked-by-question-wording » ne certifie ni réponse ni cadrage. Aucun champ ne documente une validation complète par question avec preuve, date et vérificateur. Les 414 entrées restent donc à valider selon ces axes.

## Vérifications effectuées et limites

### Navigateur — site publié initial

Écran de classe, ouverture, changements P2/P1, sélection de chapitres (tous/aucun/chapitre 14), génération P2 et P1, références attendues quand les PDFs manquent, passage à l'onglet MS, sauvegarde d'une note 4/11 et case « à revoir », ajout d'un favori : observés. Session QCM limitée à 4 pour le chapitre 14 : observée. Les données de test sont celles du navigateur distant dédié, pas celles des élèves.

Les PDFs originaux ne sont pas disponibles dans cette session : réponses A–D sur un vrai sujet, achèvement d'une session dans le navigateur, schémas/cadrages, pages MS, zoom sur un original, reconnexion réelle après redémarrage et permissions Chrome/Edge non vérifiés. Aucun PDF d'examen n'a été publié.

### Version de développement

13 tests Node exécutent le code applicatif dans un DOM simulé et avec PDF.js simulé : maximum 20 et unicité, nouvelle tentative, chapitres figés, navigation pendant une question en attente, reprise de l'état sauvegardé, conservation des notes/favoris, quota de stockage, valeurs racines invalides, priorité des erreurs, ranges de pages, rendu obsolète et destruction des documents, autoévaluation (zéro/fraction/hors plage), doublons de fichiers, activation des boutons après rendu et blocage en cas d'erreur, cadrage hors page. Syntaxe JS et diff contrôlés.

Ces tests ne remplacent pas un test d'intégration avec le vrai moteur PDF.js, un vrai navigateur et les PDFs originaux. Le serveur local de développement n'est pas accessible depuis le navigateur distant (réponse d'accès « Missing or invalid bearer token ») ; aucun contrôle visuel de la nouvelle version n'est revendiqué. Aucune mesure chiffrée de performance/mémoire réalisée.

## Étape suivante recommandée avant diffusion

1. Tester la branche avec les PDFs habituels, sur Chrome/Edge puis tablette ; vérifier une reprise de dossier après fermeture complète. Refaire le parcours de recette ci-dessous.
2. Valider en priorité les 63 cadrages signalés, les chapitres peu couverts (2, 9–11, 14), puis les autres entrées. Pour chaque ID : QP exact, numéro, page/continuation, diagrammes/options complets, lettre officielle ou marks MS exacts, chapitre(s), solution expliquée. Enregistrer validation séparée de classification, réponse, cadrage, barème et explication, avec preuve/date/vérificateur.
3. Ajouter de courtes explications Cambridge et LaTeX seulement sur des questions effectivement relues. Conserver la distinction commentaire pédagogique / MS officiel.
4. Prévoir import de sauvegarde validé, historique des tentatives Paper 2 et révision espacée selon délais (la sélection actuelle est une priorité simple, pas encore un algorithme espacé).
5. Prévoir vérification de concurrence entre deux onglets : la sauvegarde actuelle reste « dernière écriture gagnante » ; travail dans un seul onglet conseillé pendant le pilote.

## Recette manuelle avant fusion

- Exporter la progression existante ; utiliser un profil de test si possible. Vérifier les anciennes notes/favoris après mise à jour sur la même origine.
- P1 : terminer 20 QCM (ou toute la banque d'un petit chapitre), vérifier score et historique, revoir une erreur, commencer une autre session sans reset et répondre à une ancienne question.
- P1 : changer les chapitres en cours de session, ouvrir historique/P2 puis revenir et générer ; la question en attente et les chapitres de la session doivent rester les mêmes. Recharger avant/après une réponse.
- P1 : faire échouer un PDF ; A–D doivent rester inactifs. Reconnecter le dossier puis répondre. Tester « pleine page » et retour au cadrage.
- P2 : QP/MS/solution, zoom, favori, note zéro puis note maximum, révision et listes dédiées. Vérifier plusieurs pages et changements rapides pendant chargement.
- Dossier : annuler, refuser, reconnecter, changer de dossier, fichier absent, noms en double ; tester fallback sélection de fichiers sur tablette.
- Sauvegarde : recharger, exporter JSON, vérifier dernière session et bilan ; tester stockage indisponible dans un profil séparé. L'export contient la progression, aucun PDF.
